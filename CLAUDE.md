# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm start               # production start (default port 3001)
npm run dev             # dev with auto-reload via nodemon
PORT=3002 npm start     # run on a custom port
```

### Tests

Playwright end-to-end tests live in `tests/`. The config in `playwright.config.js` starts the server automatically via `webServer` (reuses an existing one on port 3001 if already running).

```bash
npx playwright test                    # run all tests
npx playwright test tests/auth.spec.js # run a single spec file
npx playwright test --headed           # run with browser visible
```

Test files: `auth.spec.js`, `dashboard.spec.js`, `pos.spec.js`, `inventory.spec.js`, `api.spec.js`. Shared login helper is in `tests/fixtures.js`. The config auto-builds `/tmp/libasound.so.2` stub on systems without `libasound2` installed (WSL/headless Linux).

There is no linter configured.

## Architecture

### Backend
- **`server.js`** — Express app. Mounts all routes under `/api/<resource>`, serves `public/` as static files, and falls back to `public/index.html` for all non-API routes (SPA routing). Exports `app` for Vercel serverless.
- **`database.js`** — Single source of truth for the schema. Uses `@libsql/client` which targets `file:pos.db` locally or a Turso remote DB when `TURSO_DATABASE_URL` + `TURSO_AUTH_TOKEN` are set. `ensureReady()` runs `_init()` once per process (promise-cached); all tables and schema migrations live there, including seed data and additive `ALTER TABLE` migrations for columns added post-launch.
- **`routes/`** — One file per resource (33 files). Each imports `{ db }` from `../database` and uses `db.execute({ sql, args })`. All route files apply `requireAuth`/`requirePermission` from `lib/permissions.js` (backed by the cookie session set up in `lib/sessionAuth.js` — see Auth below); access control is enforced server-side, not just in the frontend. Notable non-obvious routes: `categories.js` (product categories, used in inventory filter dropdowns), `denominations.js` (currency note/coin values for drawer reconciliation), `email.js` (SMTP send, credentials from `settings` table). Cross-route exports: `routes/commissions.js` exports `calcCommission` (called by `routes/transactions.js` after every completed sale); `routes/customers.js` exports `runCreditCheck` (called by `routes/accounts.js` after credit payments). Returns (`returns` / `return_items` tables) are handled inside `routes/transactions.js` via `GET /:id/returns` and `POST /:id/returns`. An exchange return (`resolution = 'replacement'`) is pending until a non-voided sale carries it as `transactions.source_return_id`; `GET /transactions/pending-exchanges` lists those for POS Hold Recall (EXCHANGE cards → `App.recallExchange` / `_startExchange`), and `POST /transactions` checks the credit with `exchangeCreditError` (exchange, uncancelled, unspent, same customer; discount capped at the return total). The Transactions screen's view box (Sales / Returns / Customer Payments) also lists account payments received via `GET /transactions/customer-payments` (`transactions` permission; excludes `writeoff`/`credit_note`; `applied_to` = allocated invoice numbers, `unapplied` = still on account). Payment receipts: `paymentReceipt()` in `lib/customerPayments.js` feeds `GET /transactions/customer-payments/:id` and `POST /email/send-payment-receipt/:id` (both `transactions` or `pos_receive_payment`); frontend `App.showPaymentReceipt(id)` (Normal print, or `printPaymentReceiptLetter()` for letter size), also opened after POS Receive Payment.

### Frontend
- **`public/index.html`** — ~9,690-line single-file vanilla JS SPA. All CSS, HTML templates, and JS live here. The entire application is one `App` object with `render<Section>()` methods (e.g. `renderPOS()`, `renderInventory()`, `renderCRM()`). `App.showSection(name)` is the router.
- **Home** — users without `dashboard` get `renderHome()` (section `home`): `showSection('dashboard')` redirects there, so POS Exit lands on it; Home is everyone's first screen after login (drivers/guards excepted), has its own sidebar item, and is where the Home breadcrumb goes. Live clock/date and Open-Meteo weather (browser fetch, no key) for the default branch's `city`/`state` (added to `currentUser.branches` in `attachBranches`; with no branch or no city it uses `currentUser.weather_branch` — the branch named 'Drax Hall', the owner's choice), geocode cached in localStorage.
- **Times** — database timestamps are UTC (`CURRENT_TIMESTAMP` text with no zone, or ISO with `Z`); the frontend shows them on the store clock, `settings.store_timezone` (default America/Jamaica, no DST), whatever the device zone: `fmtDate`/`fmtDateTime`/`_storeTime`/`_storeDateTime` parse via `_toDate`/`_utcDate`; a bare `YYYY-MM-DD` is a calendar date shown as that day. Never `new Date(dbText).toLocale…()` directly (reads it as local time), and don't pass `date + 'T00:00:00'` to the formatters. A datetime-local input is saved with `_storeLocalToUtc()` (or `new Date(v).toISOString()`); `_storeDay()` gives the store-clock day. Server side (emails, PDFs, statements/aging, A/P and Shop Use "today") uses `lib/storeTime.js` — `fmtDate`/`fmtDateTime`/`storeDay`/`storeToday` (the email router awaits `refreshStoreTz()` first); never `String(created_at).slice(0, 10)` for a day (that's the UTC day).
- **Money on documents** — always with thousands separators: frontend `App.fmt` ($1,234.50) or `App._n2` (1,234.50, no sign — foreign-currency amounts, text only, never an input's value); server documents (email/print/PDF) use `fmt`/`num2` in `routes/email.js`. CSV downloads keep plain numbers.
- **`App.api(method, url, data)`** — central fetch wrapper (`/api` prefix, JSON in/out, throws on non-2xx).
- **`App.can(key)`** — permission helper; reads `App.currentUser.permissions` (JSON blob from `security_groups`). Bidirectional: `can('inventory')` returns true if the user has `inventory` OR any of its sub-permissions (`inventory_add`, `inventory_edit`, …); `can('inventory_add')` returns true if the user has `inventory_add` OR the parent `inventory`. Use sub-permission keys to gate fine-grained features without granting the full module.
- **Auth** — `POST /api/employees/login` returns the employee record and also issues a session: `lib/sessionAuth.js` creates a random token, stores its SHA-256 hash in a `sessions` table, and sets it as an `HttpOnly`/`SameSite=Lax` cookie (`pos_session`) via `setSessionCookie`. Sessions last 8 hours with a sliding expiry — refreshed on every authenticated request, both the `sessions.expires_at` row and the cookie's `Max-Age` (re-sent by `sessionAuth`) — and are enforced per-route with `requireAuth`/`requirePermission` from `lib/permissions.js`; the frontend additionally keeps the returned employee record as `App.currentUser` in memory. Passwords are hashed with bcrypt (`bcryptjs`); legacy plaintext passwords are compared once on login and lazily rehashed to bcrypt on success. Default admin credentials on first run: username `admin`, password `123456` (forced password change on first login).

### Adding schema columns
New columns must be appended to the `migrations` array in `database.js:_init()` as `ALTER TABLE … ADD COLUMN` statements. Each runs inside an empty `try/catch` so duplicate-column errors are silently swallowed on re-runs — this is intentional, not a bug.

### File uploads (multer + Cloudinary)
- **Product images** — `POST /api/products/:id/image`, 5 MB limit, images only. When Cloudinary is configured, images are uploaded there via `lib/cloudinary.js`; otherwise stored locally in `uploads/products/` as `product-<id>-<timestamp>.<ext>` and served at `/uploads/products/<filename>`. Path persisted in `products.image_path`.
- **PO attachments** — handled in `routes/purchase-orders.js`; same Cloudinary-or-local fallback pattern, stored in `uploads/po-attachments/`, metadata in `po_attachments`.
- **PR attachments** — `/api/purchase-requests/:id/attachments` in `routes/purchase-requests.js`; same pattern, stored in `uploads/pr-attachments/` (blocked from static access in `server.js`), metadata in `pr_attachments`. Added at any stage; removable only while the request is draft/submitted/rejected.
- **WO intake photos** — `POST /api/work-orders/:id/photos` (images only, 15 MB, optional `accessory_id`), metadata in `work_order_photos`; local files in `uploads/wo-photos/` (a `PROTECTED_UPLOAD_DIRS` folder). Accessories handed in with the item are `work_order_accessories` (numbered `line_no` → A1, A2…, own `serial_number` + `description`); the item's own number is `work_orders.item_serial`. Both are added until picked up/cancelled, removable only at `intake`. At pickup (`PATCH /work-orders/:id/final-payment`) the cashier ticks accessories handed back (`accessories_returned` ids → `returned_at`/`returned_by`); any not ticked needs `accessories_note` (stored as `work_orders.accessories_pickup_note`). A Not Worth Fixing / Cancelled WO hands the item back with `PATCH /:id/return-to-customer` (same checklist, `checkAccessoryHandBack`/`recordAccessoryHandBack`); status is kept, `returned_to_customer_at/_by` record it.
- **Quote attachments** — `/api/quotations/:id/attachments` in `routes/quotations.js` (retail, rental and Special Project quotes); same pattern, stored in `uploads/quote-attachments/`, metadata in `quote_attachments`. On Special Projects, view needs `special_projects` or `special_projects_approve`; add/remove needs `special_projects`.
- **Attachment privacy** — `server.js` refuses static access to `uploads/{quote,po,rental-po,pr,payment-request,shop-use}-attachments/` (they're only served via the authenticated `/download` routes), and redirects a logged-out browser hitting one of those download links to `/?next=<link>`; `App._resumeDownloadAfterLogin()` re-opens it after sign-in. `uploads/` folders listed in `PROTECTED_UPLOAD_DIRS` (`lib/protectedUploads.js` — customer ID/reference/address-proof scans, rental and PO-approval signatures, and `approval-signatures/` — each employee's saved approval signature, stamped on approved POs/PRs/Special Projects/commission records via `resolveApprovalSignature` in `lib/signatures.js`; saved ahead of time from My Profile — `App.showMyProfile()`, opened from the top-bar name/sidebar footer — via `PUT`/`DELETE /employees/me/signature`, or for a staff member by `employees_edit` via `GET`/`PUT`/`DELETE /employees/:id/signature` on the employee form; `App._showSignatureEditor` draws or uploads, cropping and removing the paper background client-side; saving is limited to approvers — `canSignApprovals()` / `APPROVAL_SIGNATURE_KEYS` in lib/permissions.js, checked on the target employee's group for `/:id/signature`; removing is always allowed) stay static but require a session (401, or the same login redirect for a browser); emails that show those images must wrap their HTML in `inlineProtectedImages()` so they go out as CID attachments. Products and branding remain public.
- **Cloudinary** — `lib/cloudinary.js` exports `cloudUpload` / `cloudDestroy`. Configured via `cloudinary_cloud_name`, `cloudinary_api_key`, `cloudinary_api_secret` keys in the `settings` table (set through the Settings UI). Required for Vercel deployments where the local filesystem is ephemeral.

### Services & non-inventory items
`products` rows where `product_type IN ('service', 'non-inventory')` are surfaced via `renderServices()` in the frontend. There is no separate route or table — they use the same `/api/products` endpoint, filtered by type. These items have no stock tracking (`track_stock = 0`).

### Stock tracking duality
`products.stock_qty` is the global stock level. `branch_inventory (product_id, branch_id)` tracks per-branch stock separately. When `GET /api/products` is called with `?branch_id=`, the query joins `branch_inventory` and returns branch-level `stock_qty`; without that param it returns the global value. Always update both tables when stock changes.

### Units of measure
`units_of_measure` is the managed list (`/api/units`, `inventory_units`; `allow_decimal` for measured units like yards/kg). A product's stock unit is `products.base_unit_id` (NULL = Each); `product_units (product_id, unit_id, factor, price, barcode)` are its alternate units — `factor` stock units each, own price (NULL = order-only) and barcode. `GET /products` and `/products/:id` attach `units` (branch-tiered prices on the branch list) plus `base_unit_name/abbr/decimal`; the product form sends `base_unit_id` + `units` (replaced only when `units` is in the body). Lines (`transaction_items`, `quotation_items`, `layaway_plan_items`: `uom_id`, `sell_unit` name, snapshotted `units_per`; `purchase_order_items`: `uom_id`, `purchase_unit`, `units_per`) have `quantity` and `unit_price`/`unit_cost` in their unit — every stock move is `quantity × units_per` (`stockUnits()`), quantities can be decimal for an `allow_decimal` unit, and reports multiply by `COALESCE(ti.units_per, 1)` for units sold and COGS. Shared helpers in `lib/units.js` (`resolveUnit`, `resolvePurchaseUnit`, `lineName`, `parseQty`, `stockUnits`; requests send `uom_id`, legacy `sell_unit: 'case'` still resolves); variation, service and rental lines are always the stock unit. The old `products.case_qty/case_price/case_barcode` columns are folded into a "Case" product unit once at startup and then cleared. Frontend: `App._unitChoices()` / `_pickUnit()` (the unit prompt on POS, quotes, PRs and POs). Purchase request lines carry a unit too (`purchase_request_items.uom_id`/`purchase_unit`/`units_per`, resolved with `resolvePurchaseUnit`, copied to the PO line on convert). PR/PO views and the PO, GRN and Authorization to Pump documents (print, email, PDF) show a Unit column from `orderLineUnit()` (lib/units.js; frontend twin `App._orderLineUnit`), which also strips the "(Case of 24)" suffix from the item name. From a PR/PO line's Unit dropdown, "+ Add unit…" (`App._addOrderUnit`) adds an order-only alternate unit to the item via `POST /products/:id/units` (`inventory_edit`, `inventory_units`, `pr_create` or `purchasing_create`); `POST /units` (new unit on the list) also accepts `pr_create`/`purchasing_create`, while editing/deleting units stays `settings`/`inventory_units`.

### Product variations
`product_variation_types` defines attribute axes per product (e.g. Size, Color); `product_variations` holds individual SKU-level variants with their own price/cost/stock. `transaction_items.variation_id` links a sold item to its specific variant.

### Key data relationships
- `employees` → `security_groups` (permissions JSON blob), `branches` (default branch + `employee_branches` join table)
- `transactions` / `transaction_items` → `products`, `customers`, `employees`, `branches`; returns stored in `returns` / `return_items` (linked via `original_transaction_id`)
- `purchase_orders` / `purchase_order_items` → `suppliers`, `branches`; PO attachments in `po_attachments` table
- Purchase request lines have `item_type` 'sale' | 'internal' | 'service'; a 'service' line (non-physical: promo video, design work) is free-typed with its scope in `notes`, never a product, and converts to a PO line with `purchase_order_items.item_type = 'service'` + `notes` (no stock on receive, no link-to-inventory)
- Supplier-priced (fuel) purchases: `purchase_requests.request_type = 'supplier_priced'` — catalog items only, $0 cost, qty = authorized maximum; approved request prints/emails an "Authorization to Pump" (`/email/pump-authorization-preview/:id`, `/email/send-pump-authorization/:id`). Converting sets `purchase_orders.supplier_priced = 1` and `purchase_order_items.authorized_qty`; such a PO can't be sent/approved until every line is costed and a `po_attachments` row with `document_type = 'supplier_invoice'` exists (`supplierPricedProblems` in `routes/purchase-orders.js`), is received only once approved, and over-max quantities only warn
- PO currency: `purchase_orders.currency` (NULL = base, `settings.currency`) + `exchange_rate` (base per 1 unit, defaulted from `alt_currencies` by `resolvePoCurrency` in `lib/poLines.js`); all PO amounts are in that currency, receiving converts with `poRate()` for `products.cost` and the A/P bill, and `poBilling` converts received value so it compares with base-currency bills; no rate (`missingRate`) blocks send/receive. PR conversion carries `currency` and each line's `product_url` (→ `purchase_order_items.product_url`)
- POS Q items (`pos_q_item`, Q Item grid button → `App.showQItemModal`): a ticket line not in inventory (`transaction_items.is_q_item`; description, whole qty, pre-tax price at the store rate). It can be held/recalled, but a ticket with one can't be sold: `POST /transactions` refuses it, and Payment / Pay On Acct / Create Layaway stop with `App._posQItemBlocksSale()`, offering Create Quote — the line becomes a retail quote Q item and accepting the quote raises the Purchase Request as usual
- Deleting POs/PRs: `DELETE /purchase-orders/:id` (`purchasing_delete`; draft/cancelled only, refused once anything was received, billed, paid or requested for payment; a PR converted into it goes back to approved) and `DELETE /purchase-requests/:id` (`pr_delete`; any stage before conversion; unlinks its quote/WO lines). Both log a JSON snapshot in `deleted_documents`, which `lib/nextNumber.js` also reads so a deleted number is never reissued. The keys were backfilled from `purchasing_approve` / `pr_approve`
- PR/PO `internal_notes` (what it's for, for the approver; carried PR→PO on convert, shown in the approve dialog via `_showApprovalDialog`'s `context`) never go on supplier documents — `notes` is the supplier-facing field (PO print/email/PDF, Authorization to Pump)
- PO/PR lists take `q` (free-text: numbers, supplier, notes, internal notes, line item name/SKU; PRs also department/requester/PO #) alongside the existing filters; the frontend keeps them in `App._poFilters` / `App._prFilters`. `POST /email/send-po/:id` takes `to`/`cc` as arrays or comma-separated strings (`parseRecipients`), optional `subject`, and `message` (escaped, injected above the document by `withMessage`, also onto the PDF cover via `documentEmailContent`'s `{ message }`)
- PO receipts: each `PATCH /purchase-orders/:id/receive` logs a `po_receipts` row (`RCV-`, its `bill_id`) + `po_receipt_items` (qty, stock units, product `prev_cost`/`new_cost`); the frontend shows a Confirm Counts step before sending it. `POST /:id/receipts/:rid/reverse` (`purchasing_receive`, reason required) takes the stock back off, restores cost if unchanged since, voids the receipt's A/P bill (refused if it has payments), and drops the PO to partial/approved so it can be received again; refused when branch on-hand < reversal or it would go below `quantity_damaged`. Quantity received before receipts were logged (`items[].quantity_unlogged`) is reversed per line via `POST /:id/reverse-unlogged` (no bill handling). Receive items may carry `unit_cost` (PO currency, per line unit: reprices the line via `priceLine` keeping vendor discount + snapshotted `tax_rate`, then PO totals; lowering needs only `purchasing_receive`, raising needs `purchasing_approve`; refused on a line already part-received) and `selling_price` (sets `products.price` for a stock-unit line or `product_units.price` for an alternate unit; needs `inventory_edit`); logged in `po_receipt_price_changes` and returned as `receipts[].price_changes`. `PO_ITEMS_SELECT` adds `sell_price` (current price of the line's unit)
- Receiving without a PO: `direct_receipts` (`DRC-`, `supplier_id` required, `branch_id`, `vendor_invoice_number`, `bill_id`, status received|reversed) + `direct_receipt_items` (product, `uom_id`/`purchase_unit`/`units_per`, qty, `stock_units`, `unit_cost`, tax via `priceLine`, `prev_cost`/`new_cost`); `routes/direct-receipts.js` at `/api/direct-receipts`, all `purchasing_receive_direct` (purchasing sub-key, backfilled from `purchasing_receive`). By the owner's choice there's no approval: `POST /` puts stock on hand at once (products + branch_inventory + bin, `stock_movements` type `received` ref DRC-), sets `products.cost`, and raises an A/P bill (source `direct_receipt`) on the PO-receipt rule (`autoBills`); refuses a supplier invoice # already on a live receipt/bill unless `allow_duplicate_invoice`. `POST /:id/reverse` mirrors PO receipt reversal. Item history (`GET /products/:id/movements`) now also lists PO receipts and shows `stock_movements.reference`. Frontend: Purchasing → Received Without PO tab, `App.showDirectReceiptForm` / `viewDirectReceipt`
- TEMPORARY clean-up: POs received before receiving required approval can be sent back to `sent` via `PATCH /purchase-orders/:id/reinstate-for-approval` (`purchasing_approve`, reason required) — `reinstated_from_status` holds 'received'/'partial'; approve/reject restore that status (never draft/approved), cancel is blocked meanwhile, stock/receipts/A/P untouched. Safe to remove once those POs are signed off
- `products` images stored in `uploads/products/`, served at `/uploads/products/<filename>`
- `quotations` can be converted to transactions (`converted_to_tx` FK). Quoted prices: `POST /transactions` with `quote_id` charges a catalog line the quote line's `unit_price` (matched by product + `uom_id`, up to the quoted qty) while `valid_until` ≥ `storeToday()` (NULL = no expiry) and the quote isn't declined/cancelled or already converted to a completed sale; otherwise catalog price. Frontend mirror: `_quotedLineFields` / `_applyQuotedPrices` (run in `renderCart`) on Quote Recall and on recalling a quote-converted hold (`source_quote_valid_until`)
- Customer P.O. #: `quotations.po_number` / `transactions.po_number` (POS ticket field `pos-po-number`, kept on holds; a sale from a quote takes the quote's unless the cashier typed one), `rental_agreements.customer_po_number` (rental checkout, any payment method — required on credit) and `work_orders.po_number` (`PATCH /work-orders/:id/po-number`, any stage). Every invoice — Retail Tax Invoice, Rental Agreement/Settlement, Rental Tax Invoice, Service and Repair Tax Invoice — on print, email and PDF shows a Bill To box (bold name, `customer_number` as Account #, address), the P.O. # (a blank write-in line when empty) and blank Customer/Manager signature lines (Customer left off once they signed digitally). Shared helpers: `App._billToPrintHtml` / `_poValueHtml` / `_invoiceSignatureLinesHtml` and, in `routes/email.js`, `billToRowHtml` / `poValueHtml` / `signatureLinesHtml` / `blankSignatureLabels` / `BILL_TO_COLS`
- Special Project rental lines (`quotation_items.is_rental_line`, with `rental_start`/`rental_end`): approving the project creates a pending `rental_agreements` row per line (`rental_agreements.quotation_id`, `quotation_items.rental_agreement_id`) that holds the item; it can't be checked out on its own — `POST /transactions` with that `quote_id` moves it to `awaiting_issue`, then it's issued/returned through Rentals as usual. At the sale `POST /transactions` matches the quote's rental lines by product (in order): charged the quoted `unit_price`, no stock deducted (rentals never change `stock_qty`). It also refuses a rental quote's `quote_id` (rental quotes convert to agreements, never a POS sale — POS Quote Recall hides them) and any `is_rental` product without `rental_allow_sale` that isn't such a line
- `branch_inventory` tracks per-branch stock separately from `products.stock_qty`
- Bundle upsell at the POS: `GET /promotions/bundles-for/:productId` (`pos`) returns the active (`promoTimingStatus`), no-code `type='bundle'` promotions containing the item, with components and `regular_price`/`set_price`/`saving`. `App._bundleUpsell(productId)` runs after `addToCart`/`_addVariantToCart`: a non-focus-stealing card (`#bundle-upsell`, placed over `.pos-ticket-table-wrap`) lists pieces on/needed (`_bundleMissing` mirrors `computeBundleDiscount`'s counting); `_addBundleRest` adds the missing pieces; dismissed/added bundle ids go in `App._bundleSeen` (reset by `clearCart`); lookups cached 60s per product
- CRM: `crm_leads` → `crm_opportunities` → `crm_activities`; opportunities can link to quotations
- Reports hub tiles (`reports-hub` children: Marketing/Sales/Purchasing/Inventory/Accounts, gated by `reports`; Inventory (`reports-inventory`, also the 📊 Reports button on Retail Inventory) also opens with `inventory`). Inventory → Items Sold (`GET /reports/items-sold`, `requireAnyPermission('reports', 'inventory')`; per-item units/sales net of returns, `type` stock|all, `category_id` (or `none`), `brand`, `q`, `branch_id` → branch on-hand). Sales → Hourly Sales by Day (`GET /reports/hourly-sales`, `start`/`end`/`branch_id`; completed sales by weekday × hour in `settings.store_timezone` — created_at is UTC — with tickets, `gross`, `returns` (refund/credit-note returns by the hour processed; exchanges skipped — the replacement sale nets them), net `revenue`, avg per ticket (net ÷ tickets) and `days_in_range` per weekday for the per-day average; frontend `App.showHourlySalesReport`). Purchasing → Supplier Item Sales (`GET /reports/supplier-item-sales`, `period` day|week|month|quarter|year, `supplier_id` or `none`): an item's supplier is `products.supplier_id`, else the supplier of its latest non-cancelled PO; sales net of `return_items` (by return date)
- Commissions: `commission_plans` → `employee_commission_plans` (per-employee assignment) → `commission_records` (auto-created by `calcCommission` on sale/opportunity won)
- Warehouse: `warehouse_zones` → `storage_bins` → `product_bin_assignments`; `cycle_count_sessions` / `cycle_count_items` for inventory counts
- Cash drawers: `cash_drawers` → `drawer_sessions` → `drawer_reconciliations` + `reconciliation_note_counts`; `currency_denominations` provides the note/coin values used during reconciliation (base + alternate currencies; `settings.alt_currencies` entries are `{ code, base_per_unit, rate }` — Settings asks for `base_per_unit` (1 USD = 155 JMD) and `rate` = 1/base_per_unit is kept for the POS conversions; `GET /api/settings/currency` returns just `{ base, rates: { USD: { base_per_unit } } }` (API key scope `accounts:read`; RetailPOS Books reads it for its exchange rates); counted foreign notes × base_per_unit, saved as `drawer_reconciliations.fx_rates` `{ USD: { base_per_unit } }`, older rows hold the plain `rate`). The float is returned first (`float_returned`; NULL = older count that included it in `cash_counted`), expected cash = cash sales + cash account payments − petty cash (`drawer_payouts`, POS payouts against a voucher number, permission `pos_petty_cash`). All drawer report figures come from `lib/drawerReport.js` (screen, print, `POST /email/send-drawer-report/:id` PDF), including `report.summary` — all tenders as one (sales over every tender; expected/counted/variance over counted tenders) plus `overall_variance` = tenders variance + float variance; the Reconcile screen's section 4 recomputes the same sums live (`_updateReconcileSummary`)
- Accounts (AR): `customers` with `credit_enabled=1` carry `account_balance` / `credit_limit`; credit sales use `payment_method='credit'`; payments are received only at the POS by cashiers (`lib/customerPayments.js`, `/api/customer-payments`, permission `pos_receive_payment`; `POST /accounts/payments` now just returns 410) into `account_payments` with the drawer session — `payment_mode` 'open' (on account, applied to invoices later via `/:id/apply`) or 'invoices' (applied to chosen invoices). Receivables reps allocate/reallocate from RetailPOS Books via `PUT /accounts/payments/:id/allocations` (`setPaymentAllocations` — sets a payment's whole allocation list; never changes the payment), and every allocation change (Books or cashier) is logged in `payment_allocation_changes`; Books also reads `/accounts/customer/:id/receivables`, `/accounts/payments-feed` and `/accounts/allocation-totals`; unapplied amounts count against the oldest invoices in the overdue check, show in aging/statements, and payments count in the drawer's reconciliation; `runCreditCheck` auto-blocks customers whose oldest invoice still owing is past their payment terms or whose balance is over their credit limit (re-run after credit sales and payments); a manual `customers.block_override` ('block' = held by hand while current, 'unblock' = overdue but let through until current again) from the customer form's Block box (`PATCH /customers/:id/credit-block`, needs `customers_credit_block`) is applied on top — see `lib/creditBlock.js`
- TAX-EXEMPT tender: `account_payments.payment_method = 'tax_exempt'` (`TAX_EXEMPT` in lib/customerPayments.js) — only for `customers.tax_exempt`, `payment_mode` 'invoices' only, each allocation capped by `gctRooms()` (credit sale `tax_amount`, legacy invoice total × rate/(100+rate) from `settings.tax_rate`, less earlier tax_exempt allocations; `accountSummary` adds `gct`/`gct_room` to invoices), no drawer session (not in drawer counts), reference defaults to `tax_exemption_number`, no payment receipt, never reallocated; excluded from Customer Payments list and AR collections; statements/aging show it as C 'Tax exempt — GCT cleared'. Books posts Dr GCT payable (2100) / Cr A/R
- Customer aging detail: `lib/arDetail.js` `customerArDetail()` — per invoice (credit sales + legacy) due date (`created_at` + `credit_terms_days`, or the legacy `due_date`), age from invoice date, P.O. # (`transactions.po_number` / legacy `memo`), and each applied payment (P) / credit note (C) / write-off (W), plus unapplied credits; `GET /accounts/customer/:id/detail` (account view's Invoice Detail tab), `GET /email/aging-detail-preview/:id` + `POST /email/send-aging-detail/:id`. A credit-note return also writes a `credit_note` `account_payments` row (`return_id`, `CN-`) allocated to its sale's invoice (`lib/returnCreditNotes.js`; existing ones backfilled at startup); the return still adjusts `account_balance` itself, the CN row doesn't. Store credit spent on a sale (`transactions.store_credit_applied`) is drawn from the customer's open credits (credit notes first) into `store_credit_uses` (`useStoreCredit`; counted in `UNAPPLIED_SQL`, backfilled at startup). `/accounts/payments-feed` carries `return_id`/`return_number`/`return_tax` — Books books return credit notes (Dr 4900 + Dr 2100 / Cr A/R) and skips credit notes without `return_id` (legacy ones it made); refund and exchange (`replacement`) returns it reads per day from `GET /transactions/returns?resolution=…` (Dr 4900 + Dr 2100 / Cr cash, or Cr 2150 Exchange Credits Outstanding), and a replacement sale (`source_return_id`, credit in `discount_amount`) moves that credit back to sales
- Customer statements: `customerStatement()` in `lib/arDetail.js` (opening balance, period documents with running balance and each credit's applied-to invoices, closing, aged open items when the period ends today); `GET /email/statement-preview/:id`, `POST /email/send-statement/:id`, `GET /email/statement-csv/:id` (`start`/`end`), `GET /email/statements-batch` (`ids`, or `scope` balance|all; one statement per page). `POST /accounts/legacy-credit-notes` takes `apply_to_external_id` (Books' legacy invoice) and applies the note to it at entry (logged in `payment_allocation_changes` as changed_by 'RetailPOS Books (credit note entry)'; refused until that invoice is in the POS)
- Legacy invoices (old-system A/R): `ar_legacy_invoices` + `legacy_invoice_allocations` (not `transactions`/`payment_allocations`, so they never count as sales). Created only by RetailPOS Books via `POST /api/accounts/legacy-invoices` (API key scope `accounts:write`, idempotent on `external_id`), voided via `/:id/void` while unpaid. `lib/legacyInvoices.js` merges them with credit sales for open-invoice lists, oldest-first payment/write-off allocation, statements and the credit-check oldest-unpaid date — any new A/R code that lists or allocates invoices should go through it. Legacy credit notes (old-system credit owed) come the same way via `POST /api/accounts/legacy-credit-notes` (`accounts:write`, idempotent on `account_payments.external_id`) and are stored as an open `account_payments` row with `payment_method='credit_note'` and no drawer session — allocated like an unapplied payment, left out of drawer counts and the AR collections report, voidable (`/:id/void`) only while never allocated
- Accounts payable: `ap_bills` (vendor bills; `amount` is gross, `tax_amount` the GCT in it — set from the PO lines on receipt/PO bills, entered by hand otherwise; RetailPOS Books posts it to input GCT; `status` is only `open`/`void` — paid/partial/overdue are derived from `ap_payment_allocations` of non-void `ap_payments`), routes in `routes/payables.js`, shared helpers in `lib/payables.js`. `PATCH /purchase-orders/:id/receive` creates a bill per receipt (inside its transaction) when the vendor has `sync_ap` on and `voucher_default` isn't "Not vouchered"
- Vendor payment requests (Payables > Payment Request tab): vendors are paid ONLY from an approved request — `POST /payables/payments` returns 410. `payment_requests` (`PRQ-`, one vendor, `request_type` invoice|quick|advance, `po_id` for advance; draft → submitted → approved|rejected → paid, or cancelled) + `payment_request_lines` (`bill_id` for invoice lines, `description` otherwise) + `payment_request_attachments` (`uploads/payment-request-attachments/`, download-only). Routes in `routes/payment-requests.js` mounted at `/api/payables/payment-requests`: create/edit/submit/recall/cancel need `payables_requests`, approve/reject need standalone `payables_approve` (never on your own request; signature via `resolveApprovalSignature`), `POST /:id/pay` needs `payables_payments` and creates the `ap_payments` row (`payment_request_id`): invoice → allocated to the bills; quick → `createBill` (source `payment_request`) per line, then paid; advance → `ap_payments.po_id` set, left unapplied and applied to that PO's bills by `applyPoAdvances` (lib/payables.js, also called from `createBill` whenever a bill has a `po_id`). Requested amounts are capped by bill balance / PO room less other submitted+approved requests (`billRoom`/`poAdvanceRoom`). `required_date` is the requested payment date (requester; required to submit — create/edit with `submit`, `/:id/submit`, `from-po`); `scheduled_date` (+ `scheduled_by`/`scheduled_at`) is the approver's scheduled payment date — required on `/:id/approve`, movable while approved via `PATCH /:id/schedule` (`payables_approve`), cleared when a rejected request is edited; both shown separately (list, view, print, inbox sorts by scheduled then requested). From an approved/partial PO, Purchasing raises an advance with `POST /payables/payment-requests/from-po/:poId` (`purchasing_request_payment` or `payables_requests`; created already submitted; requester may attach files to their own request) — the PO view lists them via `GET /for-po/:poId`. A/P is notified via `GET /payables/payment-requests/inbox` (submitted, not own → `payables_approve`; approved → `payables_payments`), polled each minute by `App._pollPayablesInbox` (notice + count pill on the Accounts menu / Accounts Payable tile) Voiding a bill drops advance allocations (back to unapplied) instead of refusing. Print: `GET /email/payment-request-preview/:id` (`X-Pos-Document: payment-request`). RetailPOS Books only sees an advance once it's applied to a bill
- Sales credit (targets, salesperson dashboard/Transactions scoping): `COALESCE(salesperson_id, created_by, employee_id)` (`CREDITED_SQL` in `routes/transactions.js`). `ticketSalesperson()` stores the ticket's initiator in `salesperson_id` when they're an active Salesperson (POS dropdown locked to them), else the cashier's pick. `PATCH /transactions/salesperson` (`sales_manager`, ids[] ≤ 500, null clears) changes it after the sale, logged in `salesperson_changes`. Sale commission goes to the credited person; on a change `moveSaleCommissions` deletes the unpaid `commission_records` (source_type 'transaction') and reruns `calcCommission(..., asOf = sale date)` for the new person — paid records are left and returned as `commissions_paid`
- Shop Use (stock taken for company use; `routes/shop-use.js` at `/api/shop-use`, helpers in `lib/shopUse.js`, frontend `renderShopUse()` under Warehouse): `shop_use_requests` (`SU-`, category cleaning|maintenance|equipment_repair|internal_project|tools, benefiting `branch_id` + `department` (pr_departments list), supplying `source_branch_id`, separate `approval_status` draft|pending_approval|returned|approved|rejected and `fulfillment_status` not_issued|partial|issued|cancelled, `version`) + `shop_use_request_lines` (product_id or `tool_id` = borrow from the tool register; qty in the line unit × `units_per`; `qty_approved`/`qty_issued`/`qty_cancelled`; `unit_cost` = products.cost × units_per, never price). Routing: `shop_use_approval_rules` (+ `shop_use_rule_approvers`; blank branch/department/category = any, `max_amount` NULL = no limit) — `routeRequest` picks the matching rule with the lowest limit covering the total that has an approver other than the requester; approvers need standalone `shop_use_approve`, never on their own request (`approvalAuthority`); no rules = any approver. A material edit (items/qty/location/branch/dept/category) of a pending or approved request bumps `version`, clears `qty_approved` and re-routes. Issue (`POST /requests/:id/issues`, `shop_use_issue`, idempotent on `issue_key`) → `shop_use_issues`/`_issue_lines` (cost snapshot), `moveStock` (branch_inventory + products.stock_qty + bins + `stock_movements` type 'shop_use', reference = SUI-/SUR- number) and `queuePosting` in one transaction; tools-category lines create `shop_use_tools` (source 'inventory', permanent) per unit, borrow lines just assign a register tool (source 'register'). Returns/reversals `POST /issues/:id/returns` (`kind` return = `shop_use_issue`, reversal = `shop_use_finance` and puts qty back outstanding) at the original issue cost; damaged returns aren't restocked or reversed. `shop_use_postings` (one per issue/return, UNIQUE source) is RetailPOS Books' queue: `GET /shop-use/postings-feed` (API key `shop_use:read`) → Books posts Dr/Cr by account code (`shop_use_accounts` per category + setting `shop_use_inventory_account`, default 1300) keyed `shopuse:<id>` → `POST /shop-use/postings-ack` (`shop_use:write`; posted with `external_ref`/amount or failed with reason; a second posted with another ref = 409). Reconciliation (`reconChecks`: authorized / stock / value / allocation / returns) — `POST /postings/:id/reconcile` refused until every check passes. Everything is logged in append-only `shop_use_audit`. Approvers, issuers (`shop_use_issue`: approved requests not fully issued, `to_issue`) and requesters are notified in-app via polled `GET /shop-use/inbox` (`App._pollShopUseInbox`); its `count` (to approve + to issue + own requests returned) shows as a pill on the Shop Use tile and, added to the transfer count, on the Warehouse menu item (`_paintShopUseBadges` / `_paintWarehouseNavBadge`)
- Inter-branch stock: `branch_transfers` records movement between branches; `transfers` permission gates the UI. Manual transfers start as a request (`POST /transfers`, `transfers_create`, status `requested`, no stock moves); the inventory team sets the sent quantities and sends it (`PATCH /:id/send`, `transfers_approve`) — stock leaves the source then, `quantity_requested` becomes the sent qty and `quantity_asked` keeps the original ask; then `pending` → (`/dispatch`, required `driver_id` or `driver_name` → `branch_transfers.driver_id/driver_name/dispatched_by/dispatched_at`) `in_transit` → `/receive` (required `delivered_by_id` or `delivered_by_name`; each call logs a `branch_transfer_receipts` row — `received_by` = signed-in employee — with its `branch_transfer_receipt_items`, returned as `receipts` on `GET /transfers/:id`; pickers use `GET /transfers/people`). Quick transfers (`POST /transfers/quick`, `transfers_quick`, for co-located branches) do send + receive in one transaction — recorded `received` with `is_quick = 1`. Quote/work-order transfers (`lib/transfers.js` `createTransfer` without `request`) skip the request step

### WooCommerce integration
`routes/woocommerce.js` syncs products and orders between the POS and a WooCommerce store. Credentials (`woo_url`, `woo_consumer_key`, `woo_consumer_secret`) are stored in the `settings` table. HTTP stores use OAuth 1.0a signing (implemented locally); HTTPS stores use Basic Auth. `server.js` polls every 60 seconds and fires a full sync when `woo_sync_interval` minutes have elapsed since `woo_last_auto_sync`. The route also exports `runSyncAll`, imported by `server.js` for that auto-sync.
